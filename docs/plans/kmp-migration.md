# CloudStream → Kotlin Multiplatform, Compose, multimodule

Status: **plan only, nothing implemented.**
Targets: **Android only for now.** The module graph and source-set layout are the
deliverable; adding `jvm()` / `iosArm64()` later becomes a build-file change rather than
a rewrite.

## 2. Four constraints that decide the architecture

### 2.1 `:app` cannot become a KMP module
AGP 9.1.1 ships `com.android.kotlin.multiplatform.library` only — there is no
multiplatform *application* plugin (verified against resolved plugin artifacts).
So `:app` stays `com.android.application` and shrinks to a shell; everything else moves
into KMP library modules. Multimodule is not optional here — it is the *only* mechanism
by which this codebase becomes multiplatform.

### 2.2 `makeJar` is a published API contract
`app/build.gradle.kts` merges `:app`'s `classes.jar` with `:library`'s jar; third-party
extensions compile against the result. Therefore:
- Every moved file keeps its fully-qualified name (`com.lagradost.cloudstream3.*`).
  A package rename breaks every published extension.
- **Every new module must be folded into `copyJar`.** With ~25 modules, hand-listing them
  will rot. Make it programmatic (§5.3).
- `duplicatesStrategy = FAIL` is a useful tripwire — it fails loudly on collisions.

### 2.3 Strings gate ViewModel extraction
`R` is generated by the application plugin and is invisible from a library module's
`commonMain`. `shared/readme.md` asks that the 70+ locales *not* be copied into
`composeResources` until Weblate is repointed. `ResultViewModel2` has 91 `R.string` uses,
`LibraryViewModel` 9, `HomeViewModel` and `SearchViewModel` **zero**. That distribution
sets the migration order.

### 2.4 A `jvm()` target is the only thing that makes "Android only" real
With one Android target, nothing stops `import android.content.Context` landing in
`commonMain` and the module is multiplatform in name only. Every `:core:*` and
`:feature:*` module declares `jvm()` as a **purity canary** — it ships nothing, nobody
consumes it, and it fails the build on Android leakage. `:library` and `:shared` already
do this.

## 3. Target module graph

Naming follows the Now-in-Android convention (`:core:*` / `:feature:*`), which is the
de-facto Android multimodule standard and maps almost exactly onto the requested list.

```
build-logic/                    convention plugins  (NEW — see §5.1)

:library        (exists)        plugin/provider SDK — published, FQNs frozen
:app                            AGP application shell — Manifest, Activities, Services, res/
:desktopApp     (exists)

core/
  :core:common          pure Kotlin — UiText, Event, IDisposable, Vector2, coroutine utils
  :core:model           domain models, serializers, search/result/episode types
  :core:network         CloudflareKiller, DdosGuardKiller, DohProviders, RequestsHelper
  :core:data            PreferenceStore + DataStoreHelper, sync/account repos, backup
  :core:notification    channels, builders, download/subscription/installer notifications
  :core:theme           colors, palette, scheme, typography, fonts, DeviceTheme
  :core:designsystem    components: Dialog, AppBar, Pill, Slider, SettingsItems, widgets
  :core:ui              UI infra: Screen, MVI compose glue, nav contract, ComposeFragment
  :core:testing         fixtures, fakes, InMemoryPreferenceStore

media/
  :media:model          IPlayer contract, PlayerState, Video/Audio/Subtitle track types
  :media:video          CS3IPlayer, Media3 wiring, Matroska + extractors, renderers, preview
  :media:audio          audio track selection, audio focus, volume  (see §3.3)
  :media:subtitle       providers, decoders, parsers, render spans, offset, styling
  :media:cast           CastHelper, CastOptionsProvider, Chromecast subtitles, fcast
  :media:torrent        Torrent.kt + torrentserver
  :media:download       DownloadManager, download objects/utils, queue + services glue

feature/
  :feature:home  :feature:search  :feature:result  :feature:library
  :feature:downloads  :feature:player  :feature:settings  :feature:account
  :feature:setup  :feature:extensions
```

### 3.1 Dependency rules

```
                          :app
                           │  (depends on everything; owns Manifest, nav, res/)
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   :feature:*          :media:*           :library
        │                  │                  ▲
        ├──────────────────┤                  │
        ▼                  ▼                  │
     :core:ui         :media:model ───────────┤
        │                  │                  │
        ▼                  ▼                  │
 :core:designsystem   :core:network ──────────┤
        │                  │                  │
        ▼                  ▼                  │
   :core:theme        :core:data              │
                           │                  │
                           ▼                  │
                      :core:model ────────────┤
                           │                  │
                           ▼                  │
                      :core:common ───────────┘
```

Two rules carry the whole design:

1. **No `:feature:*` may depend on another `:feature:*`.** Cross-feature navigation goes
   through a navigation contract declared in `:core:ui` and satisfied by `:app`. This is
   the rule that actually prevents the graph collapsing back into a ball of mud, and it is
   the one worth enforcing mechanically.
2. **Dependencies point downward only.** `:core:common` depends on nothing internal;
   `:library` depends on nothing internal and must stay that way (it is published).

### 3.2 Which modules are KMP and which are not

| Kind | Plugin | Rationale |
|---|---|---|
| `:core:common/model/network/data/theme/designsystem/ui/testing` | KMP, `android()` + `jvm()` canary | Genuinely portable; canary enforces it |
| `:feature:*` | KMP, `android()` + `jvm()` canary | ViewModel + state in `commonMain`, Android glue in `androidMain` |
| `:media:model` | KMP, `android()` + `jvm()` | Pure contracts |
| `:media:video/audio/subtitle/cast/torrent/download` | KMP, `android()` **only** | Media3, Cast, WorkManager, SAF are irreducibly Android. The seam is `:media:model`; an iOS impl would be a sibling module, not an `actual` in these. |
| `:core:notification` | KMP, `android()` only | Same reasoning |
| `:app` | `com.android.application` | Forced by §2.1 |

Forcing Media3 into `commonMain` behind `expect/actual` would be worse architecture, not
better. `shared/readme.md` agrees: a cross-platform player is *"infeasible and
undesirable"*.

### 3.3 On `:media:audio` — a flag, not a refusal

CloudStream has no audio-only feature. Every audio hit in the codebase is a *track inside
the video player*: `AudioTrack`/`RequestAudioFocusEvent` in `IPlayer.kt`, track selection
in `CS3IPlayer.kt` (~40 lines), and volume/audio-focus gestures in
`PlayerGestureHelper.kt` (~40 lines). **Extractable today: roughly 80 lines.**

The module is in the plan as requested, and it is a defensible seam — audio focus,
track-language preference and background/audio-only playback are a coherent concern and
the place they'd land if audio-only playback is ever added. But it starts near-empty.
If you'd rather not carry an 80-line module, the alternative is an `audio` *package*
inside `:media:video`, promotable to a module later at near-zero cost. Everything else
in the requested list is backed by substantial code (§4).

## 5. Build infrastructure

### 5.1 `build-logic` convention plugins — do this first
~25 modules each repeating `kotlin { android { compileSdk = …; minSdk = … }; jvm() }`,
`jvmTarget`, opt-ins and `-Xexpect-actual-classes` is unmaintainable, and drift between
them causes exactly the runtime failures the version catalog already warns about
(`jvmTarget = 11` → `AbstractMethodError` in Compose; `jackson` 2.13.1 / `rhino` 1.8.1
pinned for `minSdk 23` on Android TV and FireSticks).

Included builds in `build-logic/convention/`:

| Plugin id | Provides |
|---|---|
| `cloudstream.kmp.library` | `android()` + `jvm()` canary, jvmTarget, compile/min SDK, opt-ins, `-Xexpect-actual-classes` |
| `cloudstream.kmp.compose` | the above + Compose Multiplatform + compiler + `libs.bundles.compose` |
| `cloudstream.kmp.feature` | the above + `:core:ui`, `:core:designsystem`, `:core:common`, `:core:model` |
| `cloudstream.android.library` | Android-only modules (`:media:*`, `:core:notification`) |

### 5.2 Enforcing the graph
The no-feature-to-feature rule (§3.1) is worth a real check, not a convention. A small
Gradle task that walks `project.configurations` and fails when a `:feature:*` resolves
another `:feature:*` costs ~30 lines in `build-logic` and prevents the most common
multimodule regression.

### 5.3 Keep `makeJar` programmatic
Replace the hand-listed `from(...)` with an iteration over the subprojects that carry
extension-facing `com.lagradost.cloudstream3.*` code, plus a smoke assertion that a known
symbol survives into `classes.jar`. Hand-maintaining 25 entries will silently break
extensions the first time someone forgets one.

### 5.4 Expected payoff
The current single 67k-LOC `:app` module recompiles almost entirely on any change.
Splitting it is the main lever on build time — changes inside `:feature:search` stop
recompiling the player. This is a concrete benefit available long before any Compose work
lands.

## 6. Phased plan

Module creation is interleaved, not big-bang. Phases 1–2 carve modules out of `:shared`,
which is **already multiplatform** — so the skeleton gets built and proven without
touching `:app` at all.

### Phase 0 — `build-logic` + jar safety · ~2–3 days
Convention plugins (§5.1); one empty `:core:common` wired into `:app`; `makeJar` made
programmatic (§5.3) with a symbol smoke check; the FQN-freeze rule written where
contributors see it.
**Exit:** `./gradlew :app:assembleStableDebug :app:makeJar` green with the new module wired in.

### Phase 1 — Split `:shared` into `:core:theme` / `:core:designsystem` / `:core:ui` · ~1 week
Pure module surgery on code that already compiles for two targets — the lowest-risk way
to prove the graph. Repoint `:desktopApp` and `:app`, then delete `:shared`.
Keep `com.mihon.*` package names as-is so the fork stays diffable against upstream Mihon.
**Exit:** the 7 existing Compose settings screens still render, desktop still builds.

### Phase 2 — `:core:common`, `:core:model`, and the `UiText` bridge · ~1 week
Move the 36 verified Android-free files. Then, in `:core:common`:

```kotlin
sealed interface UiText {
    data class Raw(val value: String) : UiText
    data class Resource(val id: Int, val args: List<Any> = emptyList()) : UiText
}
```

plus an Android-side `UiText.resolve(context)`. ViewModels emit `UiText.Resource(R.string.x)`
from `:app` call sites *today* and move to `commonMain` *unchanged* later — `Int` is not an
Android type. Convert `ResultViewModel2` (91 sites) and `LibraryViewModel` (9) in place.

**Explicitly deferred:** migrating `res/values*/strings.xml` into `composeResources`.
That is Weblate infrastructure work, and `shared/readme.md` asks for it to wait. The
`UiText` bridge exists precisely to decouple the two.

### Phase 3 — `:core:network`, `:core:data`, `:core:notification` · ~2 weeks
`:core:network` is a clean 389-LOC lift. `:core:data` is the important one: there are
**two** preference systems today — `:app`'s `DataStore`/`DataStoreHelper`
(SharedPreferences + JSON) and `:shared`'s Mihon `PreferenceStore`. Settings screens read
the second, everything else the first. Standardise on `PreferenceStore` (it already has
an `expect/actual` split and an in-memory impl for tests) backed by the **existing**
SharedPreferences file, so no user-data migration is needed. Until this lands, every
migrated ViewModel still needs a `Context` and `commonMain` is fiction.

### Phase 4 — Carve the media stack · ~4–6 weeks
Order: `:media:model` → `:media:subtitle` (3,512) → `:media:cast` (948) →
`:media:torrent` (351) → `:media:download` (3,723) → `:media:video` (6,809) →
`:media:audio` (§3.3). No UI rewriting in this phase — it is engine extraction behind the
`:media:model` contracts, and it is where the build-time payoff lands.

### Phase 5+ — Feature verticals, one per PR
Per vertical, repeat the proven Settings recipe:
1. `State`/`Action`/`Effect` + ViewModel → `:feature:x/commonMain` using
   `StateContainer`/`EffectContainer`/`ActionHandler` from `:core:ui`.
2. Screen Composable → `:feature:x/androidMain` (per `shared/readme.md`, screens are not
   shared across platforms); reusable components → `:core:designsystem`.
3. Glue: `class XFragment2 : BaseComposeFragment(), Screen by XScreen`.
4. Repoint one node in `res/navigation/mobile_navigation.xml`. **The old fragment stays**
   — that is the rollback lever the Settings migration already relies on.
5. Delete the old fragment and its layouts one release later.

| # | Vertical | LOC | Why in this position |
|---|---|---|---|
| 0 | settings | 6,673 | **Done.** Reference implementation. |
| 1 | search + quicksearch | 2,042 | `SearchViewModel`: 4 android imports, **0** `R.string`. Cleanest possible second vertical. |
| 2 | home | 2,902 | 5 imports, **0** `R.string`. Big UX win, no string blocker. |
| 3 | library | 970 | Small; 9 `R.string`, handled in Phase 2. |
| 4 | downloads | 2,829 | UI only — services already moved to `:media:download` in Phase 4. |
| 5 | account + setup | 1,410 | Biometric and package installer stay Android-side. |
| 6 | extensions | ~2,000 | `PathClassLoader`-bound; Android-only by nature. |
| 7 | result | 7,184 | 2,709-line ViewModel, 91 `R.string`, separate TV and phone fragments. Do it once the pattern is boring. |
| 8 | player | 6,760 | UI only; engine already in `:media:video`. Last. |

### Phase N — Retire the shell · ~2–3 weeks
Drop `buildFeatures.viewBinding`, delete `res/layout` (145 files) and the 61 binding
usages; replace the XML nav graph with Navigation 3 and `MainActivity` (2,076 LOC) with a
single Compose activity. Only then revisit migrating `res/values*` into
`composeResources` — with Weblate repointed first.

## 7. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A module is forgotten in `makeJar` | **Critical** — extensions fail to load | Programmatic `copyJar` + symbol smoke check (§5.3) |
| Package move breaks published extensions | **Critical** | FQN freeze (§2.2); `duplicatesStrategy = FAIL` as tripwire |
| `commonMain` silently becomes Android-only | Migration is cosmetic; next target costs a rewrite | Mandatory `jvm()` canary on every `:core:*` / `:feature:*` |
| Feature-to-feature dependencies creep in | Graph collapses back to a ball of mud | Mechanical check in `build-logic` (§5.2) |
| 25 modules × duplicated build config drifts | `AbstractMethodError`, TV/FireStick crashes | `build-logic` convention plugins **before** any module split (Phase 0) |
| Two preference systems diverge | User settings split across two stores | Phase 3 before any feature vertical |
| String migration attempted early | Breaks 70+ Weblate locales | `UiText` bridge; defer resources to Phase N |
| Big-bang Result/Player rewrite | Long-lived unmergeable branch | One vertical per PR; old fragment retained; nav-graph-only switch |
| `minSdk 23` / `jvmTarget 11` | Silent runtime crashes | Catalog already pins `jackson` 2.13.1, `rhino` 1.8.1, `conscrypt` 2.5.2 — do **not** bump during migration |

## 8. Dependencies

**No new third-party dependencies for Phases 0–4.** `build-logic` uses the Gradle/AGP/KMP
plugins already in the catalog. Phase N would need `androidx.navigation3` (or the Compose
Multiplatform equivalent) — to be proposed and approved separately when reached.
