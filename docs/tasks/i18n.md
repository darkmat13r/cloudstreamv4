# I18N — strings and localisation

The strings pipeline is built and merged. What remains is adoption, hardcoded English, and defects
in the translation data itself.

**Direction, settled (reversed):** Compose resources are the **authored source**; `app/src/main/res`
is regenerated from them. The instruction is that all strings are Compose resources with no Weblate.
This replaces the earlier "generated from `app/src/main/res`" direction, whose stated reason was
wrong: the "61 corrupted values" was a property of translate-toolkit (Weblate's reader — its
`CMPResourceUnit` overrides only writing, while reading keeps Android semantics), never of the CMP
format. This repo is not connected to that Weblate project in any case (see `I18N-05`). Plan and
progress: `I18N-07`.

## I18N-02 — Hardcoded English time units

**Status:** open · **Size:** one PR, but it touches a published ABI

`AccountManager.secondsToReadable` emits `d`, `h`, `m` — and now `s` (#26) — as hardcoded English
letters, in a function that is on the **published extension surface**
(`app/api/classes-jar.api:16463`).

Meanwhile the app already owns fully translated equivalents:

| Resource | Format | Locale files |
|---|---|---|
| `duration_format` | `%d min` | **61** |
| `next_episode_time_hour_format` | `%1$dh %2$dm` | **60** |
| `download_time_left_hour_min_sec_format` | `%1$dh %2$dm %3$ds` | 42 |

Real translations: `ru` `%1$dч %2$dм`, `ja` `%1$d時間%2$d分`, `ar` `%1$d ساعة %2$d دقيقة`.

- [x] Fix the display call sites first — `I18N-03` fixed the episode runtime
- [ ] **Two countdown sites remain, and they need a decision.** `EpisodeAdapter.kt:303` (inside
      `episode_upcoming_format`) and `ResultViewModel2.kt` `resume()` (inside `resume_remaining`)
      wrap an English `3d 4h 0m` / `2h 22m` in a translated sentence. Both spans can run to
      **days**, and no translated resource has day granularity: `next_episode_time_hour_format`
      (`%1$dh %2$dm`) is in 59 locale files and `download_time_left_hour_min_sec_format`
      (`%1$dh %2$dm %3$ds`) in 42 (re-measured; the table above says 60 and 61 — the counts
      include `values/`, measured by file and by directory). Fixing them needs either a new
      translatable string or a decision to drop the days; that belongs here, not in `I18N-03`.
- [ ] Only then consider `secondsToReadable` itself; changing what it returns is visible to
      third-party extensions, and it is used for "remaining" where seconds matter

## I18N-03 — Result page renders runtime in hardcoded English

**Status:** done

**This entry had gone stale.** It was written against `ResultViewModel2.kt:345`, which rendered
`2h 22m` through `secondsToReadable`. That half was already fixed by `cf3ce1c6` (#29) as a side
effect of `BUG-01`: the line now reads `txt(R.string.duration_format, dur)`.

The site that was actually still emitting English is `EpisodeAdapter.kt:329`, the per-episode
runtime on the result page: `runTimeMinutesToSeconds(item.runTime)?.let { secondsToReadable(it, "") }`.
The home preview (`HomeParentItemAdapterPreview.kt:372`) renders the same film's runtime as
`142 min` through the **translated** `duration_format`, so the two disagreed.

**Fix:** `EpisodeAdapter.kt` now renders `item.runTime` (minutes) straight through
`txt(R.string.duration_format, ...)`, and hides the line for a null or non-positive runtime, as
`ResultViewModel2` already does for `durationText`. Adds no translatable string and gains every
locale that has `duration_format`: **59** files under `core/strings/.../composeResources/values*/`
(the default plus 58 translations; measured twice, by file and by directory).

**Visible format change:** English users now see `142 min` where they saw `2h 22m` — the format
changes, not only the language. That is the point (consistency with the home preview). A runtime
of `0` used to render `0m`; it is now hidden.

**Trap that shaped the fix:** `apc` renders `duration_format` as `دقايق: %d` — **number last**. Any
design that concatenates two separately formatted pieces produces garbage there. The positional
resource has to be used whole, which is what the fix does.

`runTimeMinutesToSeconds` now has no production caller (only `RunTimeSecondsTest`). It stays: it
is on the published extension surface (`app/api/classes-jar.api`, `INF-07`) and deleting it is an
ABI removal.

Left for `I18N-02`: the two countdown sites, which can run to days — see there.

## I18N-04 — Hardcoded English `"0 mins"` in a ViewModel

**Status:** done · `ResultViewModel2.kt` `resume()` · the `:345` half went with `cf3ce1c6` (#29)

The only remaining literal was the `completedValue` of the `resume_remaining` argument. It is
reachable: `secondsToReadable` returns it once the position is 60 s or more past the duration
(`BUG-01`).

**Fix:** call `secondsToReadable(..., "")` and, when that returns empty, pass
`txt(R.string.duration_format, 0)` as the argument. `UiText.asString` resolves a `UiText` argument
itself, so no `Context` is needed in the ViewModel and the resource is used whole (`apc` safe).
Renders `0 min` (translated) where it rendered `0 mins`.

**Rejected:** passing `""` directly would give `resume_remaining` (`%s\nremaining`) a dangling
`"\nremaining"`; and `ResultViewModel2` has no `Context` to call `getString` with.

## I18N-05 — Broken translations, and who owns them now

**Status:** done · #40 · **Ours to fix** — see below

### The mechanism, because it is not what it looks like

`README.md:109` links a Weblate project at `hosted.weblate.org/engage/cloudstream/`, and this
repo's history carries **97 commits** titled `Translated using Weblate (<Language>)`, the most
recent dated 2026-08-26. `strings_guards.yml` recorded why that mattered, before `I18N-07` PR 5
deleted it:

> Translations reach master by push (Weblate, then `update_locales.yml`), where
> `pull_request.yml` never runs.

That was the entire reason it existed — translation pushes bypassed PR review, so the content
guards had to run on push instead. Both workflows are gone now (`I18N-07` PR 5), and the strings
guards run in `check` like every other check.

**But that was upstream.** This repo's only remote is `darkmat13r/cloudstreamv4`, and it is not
connected to that Weblate project (see `DEC-03`: separate private repo, not a fork). No bot pushes
here. The 61 locale files are a **frozen snapshot** inherited at fork time.

Two consequences, and both invert the usual advice:

- Reporting these upstream would only help upstream's users. A fix there never reaches this repo.
- **These values can be edited directly.** There is no sync to overwrite the change — but since
  `I18N-07` PR 4.2 the place to edit them is `core/strings/src/commonMain/composeResources`, not
  `app/src/main/res`, which is generated. `checkAndroidStrings` fails if the two disagree; run
  `:core:strings:writeAndroidStrings` and review the res diff.

Note also that Weblate validates *placeholders* automatically, which is exactly why the defects
below survived: `%1$dd` contains a structurally valid `%1$d`, and Hebrew `חודשים` is a well-formed
word in the wrong place. No automated check catches either.

## I18N-06 — Platform actuals for `NumberSymbols` are untested

**Status:** done for android — **measured on a device 2026-10-15, and the platforms disagree** · ios still
compile-only

`UiStringFormat` reads locale digits and separators through an `expect`/`actual`. The JVM actual is covered by 35
tests. The **android** actual was argued-by-construction; it is now measured, and the argument was wrong about the
values.

`AndroidNumberSymbolsTest` (`core/strings/src/androidDeviceTest/`) runs the same symbol table
`LocaleNumberParityTest` pins on the JVM, on a device — which is exactly the "cheapest fix" this entry asked for.
Measured on the `QA_36_1` AVD, **API 36**: **nine of the twelve pinned locales agree, three do not.**

| locale | JVM, Temurin 17.0.20.1 | Android, API 36 |
|---|---|---|
| `fr` grouping separator | `U+0020` SPACE | `U+202F` NARROW NO-BREAK SPACE |
| `ru` grouping separator | `U+0020` SPACE | `U+00A0` NO-BREAK SPACE |
| `ar` zero / decimal / grouping | `U+0660 ٠` / `U+066B ٫` / `U+066C ٬` | `U+0030 0` / `U+002E .` / `U+002C ,` |

**This is not a defect, and nothing was changed to "fix" it.** `UiStringFormat`'s contract is to match
`String.format` on the platform it runs on; the android actual reads the same two `java.text` APIs Android's own
`Formatter` reads, so on Android it matches Android. The mistake was the assumption that reading the same APIs
means producing the same output — Android's `java.text` is **ICU-backed**, the JDK's is CLDR.

**The `ar` row has a user-visible consequence worth knowing:** Arabic on a modern Android writes `1,234,567.89`,
**not** `١٬٢٣٤٬٥٦٧٫٨٩` — and always has, because that is what `String.format` does there. The `NumberSymbols` KDoc
already predicted this for **JDK 24+** (CLDR 46 moved bare `ar` to ASCII — JDK-8333582, CLDR-17553); nobody had
connected it to Android, whose ICU is already past that point. `fa` is the instructive contrast: CLDR kept Persian
digits as the default, so `fa` writes `۱٬۲۳۴٬۵۶۷٫۸۹` on both platforms.

**Why `fr`/`ru` needed measuring rather than reasoning:** both separators are spaces that print identically to
`U+0020` in any log or assertion message. That is precisely the "diverge silently" case this entry named, which is
why the test reports code points.

The suite pins **both** tables and asserts the divergence set is **exactly** `ar`, `fr`, `ru`, so it fails both
when a new locale starts to differ and when a known one stops — either is a platform change that needs the tables
and the KDoc updated together. 6 tests, 0 failures.

### What this cost, and what is still open

- The module has **no Android unit-test target**, and adding one needs **Robolectric**, which the version catalog
  does not carry — so a device test was the only route. It uses AGP's KMP `withDeviceTestBuilder`; no `:core:*`
  module had a device test before this one.
- `androidx.test:runner` has **no catalog alias**, so the source set depends on `libs.espresso.core`, which brings
  it transitively at compile scope. An `androidx-test-runner` alias would say that honestly. **A catalog change is
  the owner's call** (`dependency-security.md`), so it is flagged rather than made.
- The test is **not part of `check`** and does not run on CI, which has no emulator — that is `DEC-05`.
- [ ] **iOS is still compile-only.** Nothing checks that `ar` on iOS produces the same digits as `ar` on Android,
  and after this measurement that is no longer a theoretical worry: two platforms already disagree, so the third
  very likely does too. Needs an iOS test target, which needs a macOS runner (`DEC-05`) to be worth wiring.

**Status:** done · all steps merged (#32, #33, #34, #35, #36, and PR 5) · **Size:** six PRs, each revertible
