07Title detail and playback

The five surfaces between picking a title and watching it. They run on the shared TV chassis — 152 nav rail, chrome row y56..152, content origin x200, focus band x56..1864 / y56..1024 — and they add the three things the app cannot currently say out loud: what Resume actually resumes to, which source is resolving and why the dead ones died, and which source, subtitle and audio track are playing right now. Today the first is the bare word "Resume" on a movie and "S1:E4" on a series (ResultFragmentTv.kt:516-527), the second is a spinner over a black screen with "Skip Loading (3)" (GeneratorPlayer.kt:2367-2378), and the third exists only inside a full-screen dialog whose Apply button is visibility="gone".

The hero is 600 tall because that is the tallest hero that still fits a 56 header plus a 288 poster row inside the band, and the cast block is shorter than that row. The detail pages are one action row, and that forced two data changes. Nine independently gone/visible rail buttons are what make today's TV result page reshuffle under the user's thumb — the trailer column disappearing shifts every control to its right (fragment_result_tv.xml:307-542). 7a and 7b solve one row per state at a fixed y512 and a fixed left origin instead, which means the labels have to be short and bounded: "Season 1" must be composed from SeasonData.season as an integer, never from the provider's free-text season name, and "Episodes · 10" needs a per-season count. Neither is on ResultData (ResultViewModel2.kt:167-197) — the TV drawer reads the view-model's season state directly today, so both have to be lifted onto the detail state or the two controls degrade to "Seasons" and "Episodes". The resume label has the same shape of problem in reverse: ResultFragmentTv.kt:516-527 sets only "S1:E4", and the episode name is set on a different view nested inside resume.progress?.let { } (:490-498), so the button silently loses half its label whenever a resume target exists with no stored position. A film is worse — the branch returns the bare word "Resume" (:518) and no formatter in the tree turns ResumeProgress.progress into 1:24:07; secondsToReadable yields "1h 24m". We also made the caption two mono lines on purpose, because the bound resource is %s\nremaining (strings.xml:253) and a one-line box clips it.

7c is the screen this redesign exists to argue for, and almost none of it can be built today. A source has no identity before it succeeds: ExtractorLink.source is free text minted on a link that already landed, and loadExtractor picks its extractor by scanning a global list inside provider code (ExtractorApi.kt:932-983), so there is no denominator for "4 of 18" and no row to draw for a source that is still running. Failures are swallowed four times over — ExtractorApi.kt:948-956 logs and returns true, ParCollections.kt:110-123 maps every exception to null, APIRepository.kt:215-218 converts the whole provider call including its 120 s timeout into a bare false, and PlayerGeneratorViewModel.kt:410-427 throws that Boolean away with a trailing Unit, which is why GeneratorPlayer.kt:2345-2348 carries a commented-out acknowledgement that the provider's verdict never arrives. Attribution is discarded where it is already in scope: CrossTmdbProvider.kt:52-62 has apiName at the catch site and drops it. So the prerequisites are: a SourceId minted before work starts, an additive onSourceDiscovered hook with a default no-op on MainAPI.loadLinks (MainAPI.kt:685-699) so third-party plugins keep compiling, a per-source lifecycle and a per-source withTimeout inside the fan-out, a sealed ResolutionFailure seeded from the classification throwAbleToResource already performs and then flattens (ArchComponentExt.kt:166-201), and per-source outcomes stored in RepoLinkGenerator's 20-minute cache (:83-101) so a warm start is labelled "cached" rather than replaying a fake resolution sequence at full speed. One number on the panel is free today and simply never rendered: LinkProgress.subsLoaded (ResultViewModel2.kt:381-384).

The HUD's hard constraint was that every readout it owes already exists and is either hidden behind a preference or thrown into a Toast. The buffered band is the only element with no source on IPlayer — and even that is already in hand, read in app code at LivePreviewTimeBar.kt:26 via setProgressUpdateListener { position, bufferedPosition -> }; it needs promoting to getBufferedPosition(), not inventing. The codec and audio legs of the meta line are built by GeneratorPlayer.kt:1997-2041 but gated on show_media_info_key, default false, and setPlayerDimen emits raw "1920x1080", never a quality label. The active subtitle track is known (CS3IPlayer.kt:562-568) and displayed nowhere. Four behaviours have to change for the drawn geometry to be true: the side panel must not pause playback the way showMirrorsDialogue does (GeneratorPlayer.kt:1020, :1057-1062); auto-hide must hold for the whole buffering window rather than firing on if (player.getIsPlaying()) (FullScreenPlayer.kt:808-810); media3's own time bar must stop taking D-pad focus on TV, since exoProgress.isEnabled is only forced off on phone (:292-294) and its internal key handling scrubs by its own increment; and the player must stop popping itself off the back stack when links are exhausted (GeneratorPlayer.kt:1589-1608), because an empty state the user never sees is not a state. The replay glyph is phone-only today (PlayerView.kt:558-559), so an ended video on TV shows a stale play glyph.

Cast is on the first screen because the shipping TV app already shows it — an earlier cut of this cluster had dropped it. ActorData carries a name, an image, a character (roleString) or an ActorRole enum, and an optional voiceActor (MainAPI.kt:1524-1550); TMDB, Trakt and MyDramaList fill the performer’s name and image with the character in roleString. AniList inverts it: actor is the character, role is Main/Supporting/Background and the performer arrives as voiceActor (AniListApi.kt:119-140) — so on an anime title the name line reads the character and the role line reads “Main”, which is correct, not a binding bug. The TV result page renders it today (ResultFragmentTv.kt:449, :929-936, fragment_result_tv.xml:634-661) behind show_cast_in_details_key, default on. It takes the first-screen rail because it is about this title and More like this is about others; the 240 block is shorter than the 288 poster row, so the swap costs no geometry. The role line follows the adaptor’s precedence — the localised ActorRole when present, else roleString, else the line is removed (ActorAdaptor.kt:122-146). Three prerequisites. (1) Image mode is decided per list, not per person: ResultViewModel2.kt:235, :297-300 checks only the first actor’s image, so one missing headshot at the top turns the whole cast into a “Cast: a, b, c” text line; it must become per-person, which is what cast item 5’s initials show. (2) There is no actor id, so a cast item has nowhere to open. On TV it stays a focus stop — so the row scrolls and every name is reachable — whose only press action is the existing character / voice-actor swap (ActorAdaptor.kt:98-101) when a voice actor exists, and nothing otherwise; the phone’s long-press web search (:103-116) has no TV equivalent and is not drawn. A person page needs an id first. (3) Nothing bounds the list: the rail shows seven and “Full cast” opens the 560 panel with the rest. The avatar is a new :core:designsystem component (80dp), deliberately not a CardSize rung — a person is not media, and adding a square to the media ladder would let a poster be drawn square.

One more, found by a stricter scanner after all of the above. The check glyph in 7c's status discs was a 16×16 box rotated −45°. Its layout box is 16×16 and on the step — which is what the comment beside it used to say, and it is true of the siblings, none of which move. But getBoundingClientRect returns the transformed box, and that measures 28.28 square at a fractional origin: the diagonal of an integer square is irrational, so a rotated box can never land on the grid at any size. The fix was already in this file two rules below — .crs builds its cross from pseudo-elements and rotates those, leaving the measured element at 16×16. .chk now does the same. The rendered mark is identical; what changed is that the thing being measured is no longer the thing being rotated. It is also the second reason the icons rule gives for never hand-drawing a glyph in Compose.
