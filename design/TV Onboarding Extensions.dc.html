8First run & extensions — CloudStream 4 on Android TV

This cluster is P0 because the shipping app has no way to become useful. There is no bundled repository — PREBUILT_REPOSITORIES reads a DataStore key that nothing in the codebase ever writes (RepositoryManager.kt:100-102) — and the one control that used to lead anywhere is commented out in four layouts (fragment_setup_extensions.xml:47-51, :71-76, fragment_extensions.xml:86-91, add_repo_input.xml:31-39). A new TV user therefore lands on a home screen that reports Success(emptyMap()) (HomeViewModel.kt:329-333) — no error, no message, no call to action — and a search that silently skips submitList on an empty list (SearchFragment.kt:471). These five artboards give the first run one job, entering a repository URL, give extensions a browsable and judgeable list, and give account sign-in a path that does not require a WebView on a remote. Every number is on the 8px artboard step (4dp in the repo), every focusable box sits inside x 56..1864 / y 56..1024, and every fact on screen either binds to app source or is called out as a prerequisite in the closing note.

8a has no list, by ruling: first run is URL entry only, and no repository is built in or recommended (DEC-17). PREBUILT_REPOSITORIES is getKey<Array<RepositoryData>>("PREBUILT_REPOSITORIES") ?: emptyArray() at RepositoryManager.kt:100-102, read in eight places and written in none; both guards on it are themselves commented out (MainActivity.kt:2026, SetupFragmentLanguage.kt:76), and the only index URL that ever existed — PUBLIC_REPOSITORIES_LIST — was deleted in a565319e and now survives only inside a comment at SetupFragmentExtensions.kt:65. Shipping 8a needs no seeded or fetched index. 8a-ii promotes "Open network settings" over a Retry that provably cannot succeed (ExtensionsFragment.kt:283-291 does an app.get before a repo is accepted, so even a typed URL is rejected offline). Two more shape 8a's copy: the URL is entered in one inline field, with the name derived from Repository.name; and the clipboard prefill at ExtensionsFragment.kt:264-278 plus the short-code forms parseRepoUrl already accepts (RepositoryManager.kt:132-159) are the real no-typing routes the helper line names — nothing puts a URL on a TV clipboard any more since a565319e.

Every piece of per-plugin state these screens render is missing from the model, not merely from the UI. RepositoryData holds only iconUrl, name and url (ExtensionsViewModel.kt:21-28), so 8b's "18 available · 7 installed · checked 4 min ago" needs a cached count, a last-fetch timestamp and a reachability outcome persisted against REPOSITORIES_KEY; PluginData holds internalName, url, isOnline, filePath and version (PluginManager.kt:78-84) and toSitePlugin() fabricates four nulls (:86-105), which is why an installed plugin has no language, types, size or icon to draw. Progress and cancellation do not exist: handlePluginAction is fire-and-forget into ioSafe (PluginsViewModel.kt:157-201) and downloadPluginToFile copies the stream with no callback and no cancellation token (RepositoryManager.kt:206-212), so the bar on 8c row 2 needs both added — with the partial .cs3 deleted on cancel. Failure reasons are discarded: both downloadPlugin (PluginManager.kt:801-804) and deletePlugin (:818-820) collapse everything to false and the UI shows the bare word "Error" (PluginsViewModel.kt:193), throwing away the hash-mismatch message already written at RepositoryManager.kt:218 — that string is exactly what 8c row 6 renders. Update state never reaches a row at all: isOutdated is computed only inside the launch and manual flows (PluginManager.kt:225-240) and never reaches PluginViewData (PluginAdapter.kt:37-40), while PluginAdapter.kt:162-163 binds the repo's version identically for installed and not-installed rows. 8b's pill reads "Update available" rather than naming a target version because a boolean cannot render one, and because a plugin stuck at PLUGIN_VERSION_NOT_SET (PluginManager.kt:69) would otherwise read as outdated forever.

8c row 5 — "Needs app 4.6.0" — is a data-model change, not a label. SitePlugin.apiVersion is documented "Unused currently" (RepositoryManager.kt:58-59), Repository.manifestVersion carries two "take into account later" comments (:163, :170), and BasePlugin.Manifest has no minimum app version at all, so an incompatible plugin today simply crashes inside loadClass and degrades to a Toast over a row that still looks fine. 8b's "Update 3" is likewise a new operation: the only release-build bulk path deletes and re-downloads every installed plugin in every repository (PluginManager.kt:830-899, :862-872), and downloadAll reports download_failed only when every item fails, never naming the failed subset (PluginsViewModel.kt:135-148) — which is why initial focus on 8b sits on the first repository header and not on "Update all". An unreachable repository must also become distinguishable from an empty one: getRepoPlugins returns a bare nullable list (RepositoryManager.kt:183-191) over a parsePlugins that swallows Throwable into emptyList() (:169-178), and fragment_plugins.xml has no empty, error or loading view whatsoever. Nothing in the fetch path is time-bounded either — safeAsync converts a throw but never fires on a socket that hangs — so a screen-level deadline is required or adding a repository on 8a can hang with no exit. Finally the focus plumbing: the FOCUS_SELF traps at ExtensionsFragment.kt:196 and PluginsFragment.kt:159, the null nextFocusUp on tvtypes_chips (PluginsFragment.kt:202-203), the hardcoded 200dp bottom pad (PluginsFragment.kt:168-171), the cross-file focus id at repository_item_tv.xml:144, and PluginAdapter.onCreateContent inflating the TV layout while binding the phone binding with a // may crash (:52-58) all have to go before these rows are D-pad-navigable.

8d draws only the sign-in that the source can actually perform. Simkl is the sole provider with hasPin = true (SimklApi.kt:57-58); its device-code request (:1096-1107) and poll (:1109-1116) already exist and are already rendered with a QR by SettingsAccount.kt:156-273, so the panel is a re-housing, not a new flow. MyAnimeList and AniList declare hasOAuth2 only (MALApi.kt:42, AniListApi.kt:44), so SettingsAccount.kt:392-408 sends them to openOAuth2PageWithToast() → AuthRepo.kt:45-53 → a bare ACTION_VIEW with no WebView fallback, whose ActivityNotFoundException is swallowed at AppContextUtils.kt:614-615 after the caller has already returned true — on a TV with no browser it is a silent no-op. Their rows therefore read "Not available here"; drawing a pairing code for them would be a fiction, since a device-code path for either needs a relay that does not exist in this source. Two prerequisites gate "Manage profiles": deleting a profile calls removeKeys(keyIndex) (AccountViewModel.kt:69-90), which never matches auth_tokens/<idPrefix>/<keyIndex> (AccountManager.kt:40-62), and keyIndex is reallocated as max + 1 (AccountAdapter.kt:158) — so a new profile silently inherits a deleted profile's logged-in services. And this screen never renders at all on a fresh install: skipStartup tests accounts.count() <= 1 against the raw stored array, which is empty before any profile is created (AccountSelectActivity.kt:76-78). Signing out is drawn as "Disconnect…" rather than a bare label because a single OK on a focused row would otherwise clear a token with no confirmation, and MAL's PKCE verifier lives in a process-memory map (AuthRepo.kt:29-31, MALApi.kt:354-363) that a foregrounded browser can destroy. The fourth row, Kitsu, is the one provider on this board that can actually complete a sign-in on the TV itself — hasInApp = true (KitsuApi.kt:47), a username/password form rather than a redirect — which is why it is the row drawn connected. Its disconnected counterpart is an owed screen, not a drawn one: an in-app credential panel in the same 560 column, with the IME problem that implies.

Departures from the chassis, declared rather than drifted. (1) 8a-ii draws no chassis state view. The offline signal is a banner over content at 176..272, never a region replacement, and the disabled URL field stays underneath it on the same bands as 8a. (2) Two chassis rules are changed here and must be propagated to TV Search, TV Library, TV Detail/Player and TV Episodes/Downloads, or those files will diverge: .lgm, the rail's brand mark, moves from live #CD3D4B to ink, because live is playback state only, and a failure is a hollow neutral marker (DEC-17), which is what 8b's unreachable-repo disc and 8c's failed-install marker now draw; and .chipn moves from 20/24 to 24/32 JetBrains Mono, because a 24px line box centred in the 48-tall chip lands at +12 — (48−24)/2 — which is off the 8px step, while a 32px box lands at +8 and matches the chip label's own line box. (3) One chassis defect raised here is now fixed system-wide and one is still open. muted was #686868 — 3.77:1 on bg and 3.17:1 on raised, under the 4.5:1 AA floor at the design's own 20px type floor, which is what .ls and .chipn are set in on every row of this board. It is now #858585: 5.69 / 5.18 / 4.78. Still open: the nav rail's 8px inter-cell gap is the only pair of focusables anywhere in this file closer than 24px.
