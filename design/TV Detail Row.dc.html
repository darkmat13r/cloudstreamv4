The owner's ruling and ui-components.md rule 4 do not currently agree, and this board follows the ruling. Rule 4 says a toggle that is on is an ink glyph on a raised fill, and off is a muted glyph with no fill — so the glyph colour carries checked. The 2026-11-06 ruling says the glyph is grey at rest and white on focus, which makes the glyph colour carry focus instead, and leaves the fill alone to carry checked. Both cannot hold. Drawn here the new way, with the fill doing the work; IconOnlyToggle's KDoc and rule 4 both need editing to match, and that edit is the owner's to approve.

Worth knowing before ruling: the KDoc's reason for colouring the glyph was that a fill alone is about 1.15:1 against the page, which is why unchecked had no fill and a muted glyph. If the fill is now the only signal, checked-at-rest and unchecked-at-rest differ by that 1.15:1 and nothing else.

The skeleton's action bar has to be re-derived per type, and that is new. On 7a the loading skeleton drew one action bar from x200 to x1440 because the row was three text buttons and two cells and ended there. These rows do not: 7f ends at x1104 (552 dp) and 7g at x1344 (672 dp), measured to the last visible tile edge rather than the 96 cell edge, because the tile is the ink. The skeleton cannot know the type before the title resolves, so either it draws the shorter of the two and a film's row grows on arrival, or the bar stops being one bar and becomes the primary's 440 plus a cell-sized box per action. Drawing the shorter bar and letting it grow is the smaller jump and is what this set assumes, but it is still a jump and the owner may prefer the second. Today's built page has the same fault in a different place — the skeleton's bar runs to 1076 px against the loaded row's 1030 px at 1280 wide, a 46 px jump nobody drew.

Header order: count · provider, everywhere. The boards are inconsistent — Cast reads "38 · TMDB" in three places and More like this reads "HDREZKA · 24" in one. This set draws count first, for a reason that is in the component rather than in taste: RailHeader takes a single optional count string, so a rail with no provider shows just "38". With count first that degrades to "38" with the same element leading; with provider first the leading element changes when attribution is missing. 7i therefore reads "Episodes 24 · HDREZKA". "More like this HDREZKA · 24" on 7a-ii is the one that should change, and it is in an owner-touched file, so it is not changed here.

The cast row is at 392 dp on every board here, and the built page puts it at 358.5 dp. Nothing in this set moves it: the ladder above the cast rail — progress 592..600, caption 608..632, SectionGap 64, rail header 696..752 — is 7a's, unchanged, because the new row occupies the same y496..632 the old one did. So the 33.5 dp shortfall is in the build and not in the row, and it is not BUG-40, whose shift is a uniform 5 dp inside the head block's text ladder. It wants its own measurement against this board before any of this is built.

The one thing this whole set is really asking. Rule 2 of ui-components.md says secondary common actions are outlined, with a glyph and a label, and rule 4 says icon-only is allowed only for toggles, overflow and search, with three named exceptions — the chrome's Back cell, the player transport, and the nav rail. 7f and 7g make Start over, Trailer, Download and Mark watched icon-only, which is none of those. That is the request as it was given and it is drawn faithfully, but it is a change to DEC-17, taken on 2026-11-05, not an application of it. If the owner wants this row, rule 2 and rule 4 need rewriting in the same breath — otherwise the next screen that reaches for an icon-only secondary has a rule saying no and a board saying yes.
